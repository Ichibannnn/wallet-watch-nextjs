## 1. What is this app?

**Wallet Watch** is a personal-finance tracker with **sign-up / sign-in** and a **dashboard**
whose modules (Transactions, Statistics, Accounts, Categories, User Management) are gated by a
**role-based permission system**.

Current state:

- ✅ Authentication (sign up, sign in, sign out) — fully built.
- ✅ User Management (users + roles + a permission matrix) — fully built.
- 🚧 Finance modules (Transactions, Statistics, Accounts, Categories) — empty pages waiting for you.

## 2. The tech stack — and 3 things that will surprise you

From `package.json`:

| Tool | Job | Watch out for |
|------|-----|---------------|
| **Next.js 16** | Framework (routing, server + client) | ⚠️ Middleware is renamed **Proxy** (`src/proxy.ts`). This is *not* the Next.js in most tutorials. |
| **React 19** | UI library | The React Compiler is **on** (`reactCompiler: true` in `next.config.ts`) — you rarely need `useMemo`/`useCallback` by hand. |
| **Prisma 7** | Database toolkit (Postgres) | ⚠️ The client is **generated into your source tree** at `src/generated/prisma` — you import from there, *not* `@prisma/client`. |
| **Zod** | Input validation | Every API validates its body with a Zod schema before touching the DB. |
| **Tailwind v4 + shadcn/ui** | Styling + prebuilt components | The `src/components/ui/*` files are copy-pasted, editable component **source** — they're yours, not a locked library. |
| **bcryptjs** | Password hashing | Passwords are never stored in plain text. |

> 📌 The `AGENTS.md` warning ("This is NOT the Next.js you know") is real. Next.js 16 + React 19
> changed enough that old Stack Overflow answers will mislead you. The actual docs are shipped
> inside `node_modules/next/dist/docs/`.

**The 3 surprises, restated:**

1. **`middleware.ts` is now `proxy.ts`.** Same idea (code that runs before a page loads), new name.
2. **The React Compiler auto-memoizes.** Don't reach for manual optimization hooks by reflex.
3. **Prisma's client lives in your `src/` folder** and is regenerated by `npx prisma generate`. Never hand-edit `src/generated/`.

## 3. The folder map

Only the parts that matter:

```
src/
├── app/                        ← ROUTES. Folder structure = URL structure.
│   ├── layout.tsx              ← wraps EVERY page (fonts, theme, toasts)
│   ├── page.tsx                ← the "/" landing page
│   ├── signin/  signup/        ← the public auth pages
│   │
│   ├── (dashboard)/            ← ⭐ a "route group". The (parens) mean the
│   │   ├── layout.tsx             folder name is NOT in the URL. It exists
│   │   ├── transactions/          only to share ONE layout (sidebar+header)
│   │   ├── statistics/            across all these pages.
│   │   ├── accounts/
│   │   ├── categories/
│   │   └── user-management/
│   │       ├── users/   roles/
│   │
│   └── api/                    ← BACKEND. Each route.ts = one HTTP endpoint.
│       ├── auth/  (signin, signup, logout)
│       ├── me/                 ← "who am I + what can I do?"
│       ├── users/  roles/      ← CRUD endpoints, permission-gated
│
├── components/                 ← REUSABLE UI (dumb building blocks)
│   ├── ui/                     ← shadcn primitives (Button, Input, Table…)
│   ├── auth/  dashboard/  user-management/   ← feature-specific pieces
│
├── lib/                        ← ⭐ THE BRAIN. Non-UI logic lives here.
│   ├── prisma.ts               ← the database connection (one shared instance)
│   ├── session.ts              ← how login is remembered (signed cookie)
│   ├── password.ts             ← hash / verify passwords
│   ├── rbac/                   ← ⭐⭐ the permission system (see §5)
│   └── validations/            ← Zod schemas (the "rules" for incoming data)
│
├── generated/prisma/           ← auto-generated DB client. DON'T edit by hand.
└── proxy.ts                    ← the gatekeeper that runs before pages load
```

**The single most useful mental model:**

- `app/` = *what the user sees and hits* (routes)
- `components/` = *how it looks* (UI Lego bricks)
- `lib/` = *how it thinks* (logic, DB, rules)

When you refactor, keep logic **out** of components and put it in `lib/`.

## 4. The spine: one request, end-to-end

Trace **"an admin logs in and opens the Users page."** Understand this one flow and you understand
~80% of the app.

```
1. Browser hits  /signin  →  src/app/signin/page.tsx renders the form
        │
2. User submits → POST /api/auth/signin  (src/app/api/auth/signin/route.ts)
        │  • Zod validates email/password
        │  • Prisma looks up the user
        │  • bcrypt checks the password
        │  • createSession(user.id) sets a signed httpOnly cookie
        ▼
3. Browser navigates to /user-management/users
        │
4. proxy.ts runs FIRST (before the page). Sees the cookie exists → allows it.
        │  (If NO cookie → redirect to /signin. This is the "cheap bouncer".)
        ▼
5. (dashboard)/layout.tsx renders → wraps page in <AuthProvider>
        │  AuthProvider calls GET /api/me to ask "who am I, what can I do?"
        │  → gets back { user, role, permissions[] }
        ▼
6. users/page.tsx runs. It calls can("user-management","create") etc.
        │  to decide whether to show the "New user" button.
        │  Then it fetches GET /api/users to fill the table.
        ▼
7. GET /api/users runs requirePermission("user-management","read")
           → re-checks the cookie + permissions SERVER-SIDE before returning data.
```

### The most important idea in the whole app

There are **two layers of "can you?" checks, and they're deliberately different:**

- **Client checks** (`can(...)` in the UI) decide *what to show*. They're for UX — hiding buttons you can't use.
- **Server checks** (`requirePermission(...)` in every API route) decide *what's allowed*. They're the **real security**.

A clever user can edit the browser to un-hide a button — but they still can't get past
`requirePermission` on the server. See the comment in `src/components/auth/auth-provider.tsx`:
*"This drives UX… It is not the security boundary."*

> **Never trust the client. Always re-check on the server.** This is the #1 lesson in this codebase.

## 5. The heart: RBAC (permissions)

Three database tables (`prisma/schema.prisma`):

```
User ──belongs to──► Role ──has many──► Permission
                                         (module + canCreate/Read/Update/Delete)
```

- A **User** has one **Role** (e.g. "Admin" or "User").
- A **Role** has many **Permissions** — one row per module, with 4 boolean flags (create/read/update/delete).

So *"can Miguel edit users?"* becomes:
find Miguel's role → find that role's permission row for `user-management` → check `canUpdate`.

### The elegant part: one source of truth

`src/lib/rbac/modules.ts` defines the module list **once**:

```ts
export const MODULES = [
  { key: "transactions", label: "Transactions" },
  { key: "statistics", label: "Statistics" },
  { key: "accounts", label: "Accounts" },
  { key: "categories", label: "Categories" },
  { key: "user-management", label: "User Management" },
] as const;
```

The permission-matrix UI, the sidebar, the seed script, **and** the server checks all derive from
this array. Add one line here and the module is wired through the entire app.

> **Pattern to copy everywhere: define lists once, derive everything else.**

### Why the RBAC folder is split into two files

- `permissions.ts` — **client-safe**, no server imports, so the browser can reuse `hasPermission`.
- `guard.ts` — **server-only** (imports Prisma + cookies). Contains `requirePermission`.

In Next.js some code runs in the browser and some on the server. This split prevents database/secret
code from ever leaking into the browser bundle.

## 6. Three patterns you'll reuse constantly

### A. Every API route has the same skeleton

`src/app/api/users/route.ts` is the template:

```ts
export async function POST(request) {
  try {
    await requirePermission("module", "action");          // 1. authorize
    const data = schema.safeParse(await request.json());  // 2. validate
    // 3. do the DB work with prisma
    return NextResponse.json({ /* ... */ }, { status: 201 });
  } catch (error) {
    return authErrorResponse(error);                       // 4. handle auth errors
  }
}
```

Copy this shape for any new endpoint.

### B. The session is stateless and signed

`src/lib/session.ts`. There is no "sessions" table. The cookie holds `userId.signature`, where the
signature is an HMAC using your secret `AUTH_SECRET`. The server trusts the userId because the
signature can't be forged without the secret. The file's own comments explain how to upgrade to a
DB-backed session later (e.g. if you need "log out everywhere").

### C. Prisma is a shared singleton

`src/lib/prisma.ts`. The `globalForPrisma` trick prevents creating hundreds of DB connections during
dev hot-reloads. **Always** `import { prisma } from "@/lib/prisma"` — never `new PrismaClient()`.

> The `@/` in imports means `src/` (defined in `tsconfig.json` → `paths`).
> Example: `@/lib/prisma` → `src/lib/prisma.ts`.

## 7. How to run it locally

You need a Postgres database and a few env vars in `.env`:

- `DATABASE_URL` — pooled connection (used by the app at runtime)
- `DIRECT_URL` — direct connection (used by Prisma for migrations/seed)
- `AUTH_SECRET` — random 32-byte hex string used to sign session cookies

Generate a secret with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Then:

```bash
npm install
```

```bash
npx prisma db push
```

```bash
npx tsx prisma/seed.ts
```

```bash
npm run dev
```

Open http://localhost:3000.

### What the seed does (`prisma/seed.ts`)

- Creates two system roles:
  - **Admin** — full CRUD on every module.
  - **User** — read-only on the finance modules; **no** user-management.
- Backfills any pre-existing account (that has no role) to **Admin**, so you're never locked out.
- New self-signups get the **User** role.

## 8. Roadmap: how to add a new feature

The finance modules are empty shells. When you build, say, **Transactions**, the recipe is:

1. Add a `Transaction` model to `prisma/schema.prisma`, then run `npx prisma db push`.
2. Create `src/app/api/transactions/route.ts` following the skeleton in §6A.
3. Add a Zod schema in `src/lib/validations/`.
4. Build the page at `src/app/(dashboard)/transactions/page.tsx`, using `useAuth().can(...)` to gate
   buttons — copy the pattern from `src/app/(dashboard)/user-management/users/page.tsx`.
5. `transactions` is **already** in the `MODULES` list, so permissions + sidebar already work.

## 9. Glossary

| Term | Meaning in this project |
|------|--------------------------|
| **Route group** `(dashboard)` | A folder wrapped in parens. Groups pages under a shared layout **without** adding to the URL. |
| **Route Handler** | A `route.ts` file under `app/api/`. Exports `GET`/`POST`/etc. functions = your backend endpoints. |
| **Proxy** | Next.js 16's renamed "middleware" (`src/proxy.ts`). Runs before pages; does the cheap cookie-presence redirect. |
| **RBAC** | Role-Based Access Control. Users → Roles → Permissions (per module, CRUD flags). |
| **Server Component vs Client Component** | Files with `"use client"` at the top run in the browser (can use state/effects). Everything else runs on the server by default. |
| **Singleton** | One shared instance for the whole app — here, the Prisma client. |
| **HMAC** | A cryptographic signature. Proves the cookie's userId wasn't tampered with, using `AUTH_SECRET`. |
| **`@/`** | Import alias for `src/` (set in `tsconfig.json`). |
